# 项目Git · 项目导入

把散落的项目材料，按约定 JSON 导入本机的「项目Git」，它会自动标准化并画成提交图（主干 / 分支 / 终止 / 合并 / 里程碑 / 材料）。

## 什么时候用

- 用户要把一个进行过或进行中的项目搬进来
- 用户希望看到「做过哪些决定、哪条路走错了、材料在哪」
- 用户要「能问」这个项目（导入后可用应用内「问一问」）

## 导入流程

### 1. 抽取条目

从用户的材料里抽出**事件**，不是段落。每条对应图上的一个节点：

| type | 什么时候用 | 例子 |
|---|---|---|
| `决策` | 定了某个做法 | 放弃 HID，改 GATT 直连 |
| `方案` | 打算怎么做 | 先做单机版验证想法 |
| `复盘` | 事后总结 | 第一轮标注一致性 0.61 |
| `资料` | 文档、笔记、协议 | 交接文档 |
| `数据` | 语料、样本、日志 | 冲突用例 32 条 |
| `代码` | 仓库、脚本 | star-ticket-router |
| `产出` | 论文、报告、发布 | 课程设计报告 |

**走错的路一定要单独成条**：`status: "已放弃"`，并用 `branch` 给它一条分支名（如 `feat/lan`）。这是本工具最有价值的部分。

### 2. 串关系

用 `parents` 指向上一条。分叉就指向分叉点；合并就写两个 parent。

### 3. 写 JSON

参见 `docs/INGEST.md` 的完整字段说明。最小可用示例：

```json
{
  "project": { "name": "示例 · 课程设计" },
  "nodes": [
    { "key": "a", "type": "方案", "title": "先做单机版验证想法", "date": "2026-03-02" },
    { "key": "b", "type": "决策", "title": "放弃单机版，改为联网协作", "date": "2026-03-15", "parents": ["a"], "extra": { "理由": "单机版没法验证协作冲突" } },
    { "key": "c", "type": "决策", "title": "试过本地局域网直连", "date": "2026-03-20",
      "status": "已放弃", "branch": "feat/lan", "parents": ["b"], "extra": { "理由": "跨网段就找不到设备" } }
  ]
}
```

### 4. 先 dry-run

```bash
node tools/ingest.js batch.json --dry-run
```

看 `warnings` 和 `created`。没问题再正式导入（去掉 `--dry-run`）。

### 5. 打开应用

切到该项目即可看到图；「问一问」里可以立刻提问。

## 必须遵守

1. **不要编造 source**：没有原文文件就不要写 `source.file`，否则点开是空。
2. **日期用内容发生的日期**，不是今天。
3. **一条一个事件**：不要把一整段纪要塞进一个 title。
4. **已放弃 ≠ 删除**：放弃的条目要导进来，这是历史。
5. 导入前提醒用户：应用会先备份到 `data/state.before-ingest.json`。

## 返回给用户的话术

> 导入了 N 条（新建 X / 跳过 Y），生成 M 条关系。其中 K 条是已放弃的尝试。
> 打开「项目Git」切到「项目名」就能看到图；点卡片可以看依据和原文。
